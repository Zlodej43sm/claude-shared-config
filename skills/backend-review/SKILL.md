# backend-review — review backend code against the house standards

Generic and reusable: no company or project data lives here. The rules come from two places, read every time:
1. `backend-implementation` skill (`../backend-implementation/SKILL.md`): the generic rules, §1–§10.
2. The project's standards: follow the root `CLAUDE.md` / `AGENTS.md` (workspace and repo) to its coding-standards, style and review docs (typically `docs/coding-standards*.md`, a `--review` doc per repo) and any project-local review skill (e.g. a migration checklist). If the project documents its reviewers' expectations, review with those reviewers' questions.

Order of authority: repo `CLAUDE.md` → project docs → generic rules. A finding cites the rule it breaks (doc path + section, or skill §).

## Step 1 — scope
- Get the diff against the base (`git diff <base>...<head>`), the PR description and existing review threads. Read the changed files whole, plus the callers and sibling modules they touch (same layer, same domain).
- A schema-only PR (migration) whose code ships in a linked PR: read that PR's use of the new column too (comparisons, precision, null meaning); the semantics live there.
- A caller PR that depends on a provider PR in another repo (types, a new field): read the provider PR's head and its open review threads too. A rename or boundary change asked there changes this PR (field name, `<` vs `<=`, the date shown); check the pinned prerelease matches that head.
- Bot review comments: check each against the current head before relying on it; one that describes code not in this PR is stale, so list it for a decline-and-resolve reply.
- Note the component type (from the project docs): it decides which rules apply.

## Step 2 — check, in this order
Use the groups of `../backend-implementation/references/review-checklist.md` as the frame; the items below are the details per group.
0. **Architecture:** component responsibilities; read/write split (decisions and read-after-write on the primary).
1. **Contract and behaviour:** request/response schemas, breaking changes (stricter schema, renamed field, removed field) and whether every caller was checked; a new field callers don't send yet follows expand-then-contract (optional → callers released → no caller omits it → required) with the follow-up ticket named; strict validation against another service's enum (version skew); edge cases aligned with sibling methods (empty input, not found, duplicates); every new response field has a consumer linked in the PR (otherwise ask "Is this needed?"), and a nullable one says what `null` means; a field newly read from a cached or unreleased upstream response is normalised (missing → `null`) or the cache key changes — trace what each consumer does with `undefined` (`!== null` is true for it); public API fields use their sibling types' names and types ("the other shortcuts use `endDate`"), are additive, and a period end is checked and shown with the provider's boundary rule; user-facing sentences are one ICU key each, dates shown in the owning entity's time zone; no prerelease pin left at merge.
2. **Layering:** no query in a handler; no read-then-write in a model (full-entity upsert = one `ON CONFLICT` statement; replica lag and parallel calls); providers run one query with no `if`/`throw`/maps/second query/`getOrCreate`; models hold the decisions; write-time concurrency conditions stay in SQL; no cross-provider calls. For each new provider or model wrapper, find the existing one on the same table and ask whether it could take an optional filter or partial changes instead ("What about a generic `update<Entity>` that updates only the provided properties?").
3. **Types:** storage records independent of API types; inline provider input types; references reuse the owning entity's field schema.
4. **Data rules:** upsert = full replace; business value ranges in the schema; ordering-key precision and tie rule; a deleted model check moved into the schema; the same tie rule in the model and in SQL; internal ids and DB-managed columns not accepted from callers; optional links `.nullish()`; batches de-duplicated in the model; placeholders for parent-after-child; a sync from an external source follows backend-implementation §3 (absent clears, malformed keeps and logs, write only on change); external date strings parsed strictly (try a date-only and a locale string: where does the cut-off land?); lookup maps built only from the rows they are read with.
5. **Errors and logging** (`../backend-implementation/references/logging.md`): project error classes with cause; no double logging; the logger's error key keeps stack and cause; no whole payloads, secrets or personal data in new log lines.
6. **Security and config:** parameterised queries, permission checks, no secrets, bounded caches; time-dependent decisions taken after the cache read, never cached. For a security/fraud/eligibility fix, trace every entry point that performs the action (the action method itself, workers, replays), not just the preflight method the PR changed — a rule only in `can…` is bypassed by calling the action directly; check it fails closed when its input is missing (blocking unless the PR names a short, ticketed fail-open window); on the caller side, a missing record (user not found) stops with the not-eligible error instead of forwarding `undefined` to the downstream rule.
7. **Tests** (apply `../test-design/SKILL.md`; report each duplicate with the test that already covers it): unit tests for every model branch (dependencies mocked, calls and results asserted); no provider unit tests; functional scenarios for every behaviour change and bug fix against the real test DB; outbound HTTP mocked; affected `select *` features updated; test-table cleanup order. Flag as should-fix (ask to delete): any unit or functional test that only checks schema validation (types, integers, required fields, enums, formats) at any entry point — service methods, API and webhook routes (invalid payload → framework 400), consumers — and any mocked downstream validation error the code doesn't react to in its own way; failure scenarios that don't assert the error message/code or error data; scenarios already covered by a combination of others; model-only logic (dedup, normalisation) tested functionally or fed dirty fixtures. A test that pins a temporary behaviour (fail-open while a field is optional) is named as such and listed in the follow-up ticket; functional tests the author could not run locally are confirmed green in CI; a date or threshold rule is tested on each side of the boundary.
8. **Naming and style** (backend-implementation §10 + the project's style doc): every new or renamed test and scenario title copies the form of the titles already in its file, then its sibling files, then the repo's most common form (test-design Step 3); a title that breaks that form is a naming suggestion, with the title rewritten in the file's form (not in the default form). Only when there is nothing to copy, scenario, test, method and response descriptions, response fields, schema/type, model and provider names, cross-entity fields and file placement follow the project's naming doc, else the default forms of backend-implementation §10. Every new column/field name: grep the repo for the concept and ask for its existing word and pair ("What about `<field>_to`? It pairs with `<field>_from`"), then check the reused name keeps that pair's boundary rule (exclusive end) in the code that compares it. After a rename, grep the old word across the stacked PRs. Collection names say what they hold: read each name and ask what a reader would believe about its rows (`…WithEndDate` while the end date can be null; `…ValidKeys` while invalid keys are in the set). File names short, in an existing module's family.
9. **PR description:** matches the code (missing-field behaviour, defaults, contract changes, test counts); says where a new rule is not enforced (paths left to another system) and lists manual pre-release steps with exact values.
10. **Scope and readability:** no drive-by changes; no intent comments (only DB/library quirks); one job per function, matching its name; names carry meaning; PR title and description true.
11. **Simplicity** (backend-implementation §11; ask "why do we need this?"): single-use mappers, wrappers and helper files inlined; schema library only at input; defensive checks justified by the source's documented model; one error path unless the caller needs two; test-only side effects don't change the response; existing log lines kept and new ones log only needed fields (no whole objects or payloads, nothing the framework already logs); no magic literals; one `as const` source per set of values; shared constants and errors generic; only the events the ticket needs; code feeding other teams' data not reshaped.

## Step 3 — report
- Findings ranked: **blocking** (wrong behaviour, broken contract, layering or security), **should fix** (standards), **suggestion** / **[nit]** (style and naming). Each finding: `file:line` — what is wrong (rule cited) — **How it can fail** (a concrete input or timing, e.g. two parallel calls, a redelivery, a lagging replica, a 0 value) — **Solution proposal** (code or exact title).
- For a naming or wording fix, give a ready-to-apply suggestion block, the way reviewers do:
  ````
  ```suggestion
    Scenario: Should ignore an update when the update timestamp is older than the existing one
  ```
  ````
- For a rename, say what the current name makes a reader believe that isn't true, and list every other line that needs the same rename ("Line 64 needs the same rename").
- Ask a question instead of asserting when the intent is unclear ("What do the other batch methods return for an empty list? Could we align?").
- A should-fix that needs a decision first (which rule is right, should two places agree) is labelled `should-fix (decision needed)` in the review, and only its comment text is written the way a human reviewer would: short, in plain words, with only the facts needed to answer it and no label in the text ("`getX` uses the country rate but `getY` only the default one, so the two pages can show different numbers. Which one is right? If it's the country rate, should we open a ticket to align `getY`?"). Every other finding keeps its usual label.
- Don't flag what the project docs mark as accepted, and don't re-raise points already answered in the threads.
- Read-only: don't edit code, don't post comments, don't resolve threads unless the user asks.
