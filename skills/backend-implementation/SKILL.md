# backend-implementation — backend coding standards

Generic and reusable: no company, product or project data lives here. Project-specific rules (component types, frameworks, error classes, logger, test tooling, naming, review lessons) live in the project's docs; this skill reads them and applies them first.

## Step 0 — load the project's standards (every time)

1. Read the root `CLAUDE.md` / `AGENTS.md` of the workspace and of the repo you change. Follow their pointer to coding standards (typically `docs/coding-standards*.md`, a conventions doc, or a project-local skill) and read those chunks.
2. Order of authority: repo `CLAUDE.md` → project coding-standards docs → this skill. When a project doc is stricter or names a concrete tool, error class or naming scheme, use it.
3. No project standards found: apply the defaults below and say so in your plan or review.
4. When unsure how something should look, copy the newest repo or module of the same kind in the project, not the older code next to your change.
5. Review lessons: propose a generic lesson for this skill (and `references/review-checklist.md`) and add it only after the user agrees, since these files are shared by every linked project; a project-specific one goes into the project's docs.
6. Before opening a PR and after every push, run `references/review-checklist.md` (grouped like reviewers' feedback: architecture, contracts, data, tests, naming, organisation, errors, process). If the change adds or edits docs (`*.md`, ADRs, READMEs, glossary, code comments that describe behaviour), also run the `doc-review` self-check (`../doc-review/references/self-check.md`) on them.
7. When reviewers disagree, follow the more specific or newest convention and say in both threads what you did and why.
8. If the project documents its reviewers' expectations (a reviewer-profile or review-lessons doc), read it and write the code those reviewers would approve on the first pass.

## 1. Components and layering

- Respect the project's component types (what each may call, own and publish). Never put domain rules in a component that doesn't own the domain; one component wraps each third-party API.
- Inside a component: **handler** (thin: validate, call one model, map errors) → **model** (business logic) → **provider/repository** (data access) or **client** (outbound calls). A handler never queries; a provider never decides.
- **Provider / repository:** one query against one resource. Plain verbs over full rows: `get<Entity>(filters)`, `get<Entities>(filters)`, `insert<Entity>`, `update<Entity>`, `delete<Entity>`; name a write that may skip rows after its condition (`upsert<Entities>IfNewer`); an insert-or-return-existing keeps the plain `insert<Entity>`. Not in a provider: `getOrCreate`, single-column getters, `if`/`throw` on results, de-duplication, maps, a second query, calls to other providers, caching. Parameterised queries only.
- **Extend before adding:** before writing a provider, look for one on the same table. A new filter becomes an optional field of the existing `get<Entities>(filters)` (optional `where` clauses are query building, not decisions). A new column to write becomes an optional field of the existing `update<Entity>(key, changes)`, which writes only the fields provided (`undefined` leaves a column, `null` clears it). No `get<Entities>With<Condition>` or `update<Entity><Column>` siblings, and no second model wrapper copied from the first.
- **Compose from providers, not from another model's response:** a model that needs raw rows calls the providers itself. Calling a sibling model hands you its API contract: a `Date` already turned into an ISO string (you parse it back: a round trip), a default hidden behind an override (you query again to get it). Count the queries on every path and write the version with the fewest ("up to 3 where 2 are enough" is a finding). Reuse a sibling model only for its result as such; reuse a rule through a shared helper (§11).
- **Concurrency exception:** a condition that must hold at write time stays in the SQL statement (`ON CONFLICT … DO UPDATE … WHERE stored <= incoming`, insert-or-return-existing). The model must not replace it with read-then-write.
- **Full-entity upsert = one statement:** when the request carries the whole entity, the provider runs one `INSERT … ON CONFLICT (<key>) DO UPDATE` (`upsert<Entity>`); the model never reads the row to choose insert vs update — that races under parallel calls and a lagging replica.
- **Model:** skip empty input, de-duplicate, resolve links, check existence, throw domain errors, orchestrate providers/clients, map records to API types. One function, one job: a function's name states everything it does (a de-duplicator doesn't also normalise). Inline single-use logic; a local helper only when its name states a concept.
- **Read/write split:** when reads go to replicas by default, a read that decides a write, or follows a write in the same request, uses the primary (or the decision moves into one SQL statement).
- Pre-push check: any provider with an `if`, a `throw`, a map or a second query? Move that part to the model.

## 2. Types and contracts
- Storage record types describe columns; API contract types describe requests/responses. Keep them independent: never alias or derive one from the other. Providers take/return records; models map to API types.
- Type provider inputs inline from the record (`Pick<…>`, `Partial<…> & Pick<…, 'key'>`); don't export one-off input aliases.
- Contract changes go into the project's shared types package and are regenerated/published per its docs. Prefer `type` aliases and `as const` dictionaries over interfaces and enums unless the project says otherwise. A module used only for types is imported with `import type`.
- Validating a request field against an enum owned by another service (imported from its types package) rejects any value that service adds before your pin is bumped. When the code checks only one value, accept a string and compare; otherwise keep the pin aligned with the caller's and bump it on release.
- Every new response field has a named consumer: the PR description links the caller change that reads it. Without one, leave the field out (reviewers ask "is this needed?"). A nullable field's description says what `null` means; a timestamp is an ISO 8601 string with offset.
- A field newly read from another component's response can be missing: in cache entries written before your deploy (for up to the cache TTL) and from a provider not released yet. Normalise it once where it enters the model (`?? null`) or change the cache key; code after that checks one empty value, never `!== null` on something that can be `undefined`.
- Public API fields (read by apps or other teams) take the names and types their sibling types already use (siblings have `endDate` → not `endsAt`), say whether an end is included, and are additive so old clients keep working. A consumer of a period end compares and displays it with the provider's boundary rule: with an exclusive end, hide at `now >= end` and show the last included day, not the end itself.
- Sentences the backend builds for users: one translation key per sentence, with ICU `select`/`plural` for the variable parts (a country, whether a date exists), never concatenated fragments. A date in user-facing or legal text is shown in the owning entity's time zone, not the viewer's.

## 3. Entities, upserts, batches
- A concept with its own lifecycle is its own entity (type, table, methods), linked by id.
- Upserts replace the whole entity (PUT): non-partial request schema, required fields enforced by the schema, a missing optional link clears it. Callers never send internal ids: omit the internal key, accept the external one, resolve it in the model.
- Parent may arrive after child: the model reads the parent and, if missing, inserts a placeholder with only the external id; the parent's own upsert fills it.
- Ordering keys (update timestamps, versions): know their precision (e.g. dates truncated to milliseconds), expect equal values, and define the tie rule explicitly.
- Batch methods only when callers send several items: array input, plural name, one statement, keys de-duplicated in the model first (same key twice: newest version wins, ties go to the later item). The same tie rule holds in SQL against stored rows (`<=`): later notification wins everywhere, and a redelivery just rewrites the same values. Empty input returns an empty result without touching the database. The response holds the rows actually written; skipped (stale) items are not echoed. Otherwise single-item functions.
- Request schemas omit internal ids and database-managed columns (`updatedTs`, generated uuids); timestamps the caller owns (the source system's created/updated time) stay in the request. An optional link is `.nullish()`, so `null` and absence both clear it.
- When you delete a model check, move its rule into the schema (e.g. a removed `!amount` guard becomes `.positive()`) or state in the PR why it is gone.
- Making a schema stricter (partial → full replace, optional → required) is a contract change: check that every caller already sends the fields, and say so in the PR with the release order.
- A new field a caller doesn't send yet ships in two steps (expand, then contract): (1) release the service with the field optional, (2) release the caller sending it, (3) confirm from logs/traffic that no other caller omits it, (4) release the service with the field required. The PR states the steps and links the follow-up ticket for step 4.
- **Sync from an external source of truth** (a job copying config from a third party into the database): a key absent at the source clears the stored value; a malformed value keeps the stored value and logs the bad key; a missing target row is logged and skipped; only rows whose value changed are written (compare dates by time value, not by reference), each write logging the previous and new value. Each parser handles one family of keys and the other parsers skip that family explicitly, so a new family is never reported as invalid by an older parser.

## 4. Validation
- Validate every input at the boundary with the project's schema library, internal callers included. The schema checks shape; normalising values (trim, drop empty, de-duplicate) is a model decision. Build request schemas from the entity schema (omit/partial, then extend). Invalid input fails in the schema, not in the model.
- Encode business value ranges in the schema (positive amounts, non-empty names, max lengths), not only types.
- Map input to explicit fields; never spread raw input into records or queries. Cap sizes on public endpoints.
- The schema library runs only at the boundary (route or method input). A third party's required fields go into that input schema, taken from its documented model (SDK types, API reference); never re-validate (`safeParse`) inside the domain.
- No defensive checks for states the source's documented contract makes impossible. Before adding one, check the source's model; if you can't say how the state happens, don't handle it.
- Parse dates from external input strictly: a full ISO 8601 date-time with offset, anything else is invalid. `new Date(value)` also accepts date-only strings (read as UTC midnight) and locale formats (read in the server's time zone), which silently move a cut-off.

## 5. Errors and logging
- Quick reference with the full logging rules and a pre-push check: `references/logging.md` (read it before touching a log line or a thrown error).
- Throw only the project's base error class or its subclasses, with a code and a functional/technical classification; never bare errors or strings. One class per failure mode.
- Re-throw a caught error as is only if it is already a project error; otherwise wrap it, keeping the original as `cause`. Static messages; variable data in structured info.
- Use the project's logger, never `console.log`. Log a failure once: either throw with context and let the framework log it, or log once in the model and throw the wrapped error (follow the project's pattern); never log it again in another layer. Structured fields with the error under the project's key — check that this key really serialises the error (stack, cause); if the lint rule and the logger disagree, follow lint and raise it centrally; no whole objects, secrets, tokens or personal data. Levels: debug, info, warn (monitored), error (must be fixed).
- One error path unless the caller really needs two: when the caller reacts the same way to every failure, let the error reach the framework (it logs once and answers 5xx) instead of special-casing error kinds.
- A side effect that only serves testing or monitoring (a CI trigger, a metric, a notification) never changes the response to the caller: log the error and answer success.
- Before adding or changing a log line, read the project's logging guideline. Keep an existing log line unless it is wrong. Log the few fields you need (ids, types, counts), never a whole object or payload: every property becomes an index field (the index can hit its field limit and stop indexing) and objects you don't control leak personal data. A stringified object in one field is the exception for when you really need all of it, not the default. Don't add a log the framework already writes (request/response and error logs, often with the payload) or one only to carry context: add fields to the logger or a child logger. Don't log fields the platform already adds (environment, application).

## 6. Config, cache, security, dependencies
- Config through the project's config system; secrets only in its secret store, never in code, config files or logs. Constants in a `constants` module; no magic values, including literals in conditions (`length === 0`, status codes, limits): name them, or use the project's accepted idiom.
- One source of truth per set of values: a dictionary declared once `as const`; derive the list (`Object.values`), the union type (`(typeof X)[keyof typeof X]`) and a type guard (`isX(value): value is X`) from it, instead of a second hand-written array or enum of the same values. An exported list constant is typed `readonly T[]`, so no importer can mutate it; a response type is mutable, so copy it when it goes into a response (`[...LIST]`).
- Cache only where the architecture allows it; every cache has a TTL or size bound. Cache the raw upstream data and take time-dependent decisions (expiry, opening hours, eligibility windows) after the cache read, so they are exact whatever the TTL.
- A security, fraud or eligibility rule is enforced by the operation that performs the action (create, cancel, refund), not only by a preflight `can…`/`check…` method the client is expected to call first; both use one shared rule function. Find every entry point that reaches the action (other methods, workers, replays) before calling it fixed.
- Such a rule fails closed: a missing input it needs denies the action. If a rollout forces a fail-open period, state it in the PR, name the follow-up ticket, and keep the window short. A caller that loads the data for the rule (the user, the account) handles "not found" itself with the not-eligible error, instead of passing `undefined` on and relying on the downstream service to reject it.
- Check ownership and permissions on every request, deny by default; allow-list outbound URLs and file paths built from input; no `eval` or shell commands with input.
- Ask before adding a dependency; upgrade majors one at a time, then build and run all tests.
- A container start script does its setup (migrations, certificates), then `exec "$@"`, with the default command in `CMD`: every process the image runs (API, worker, one-off command) gets the setup and receives signals directly. Before you fix a start command, read the epic's planned tickets and the sibling repos' entrypoints for other processes that will run the same image. Before docs or values rely on a deploy key (`args`, a probe, a hook), confirm that the chart version in use renders it: read the chart, or a sibling that uses the same version.

## 7. Readability
- Names carry the meaning: intent-named functions, named booleans, variables naming the situation, response fields naming what they hold.
- A collection's name says exactly what it holds. Name query results after the filter that produced them (`<rows>Matching<Input>`), not after a property some rows lack (`<rows>With<Field>` when the field can be null). A set that also holds invalid entries carries no "valid" word. A wrong name makes the reader misread the logic (why doesn't an invalid value clear the stored one?).
- Build a lookup map only from the rows it is read with. Merging two result sets into one `Map` lets the later row silently override the earlier one and keeps keys nobody reads.
- No comments for intent or business reasons (they go in the PR description) and none that restate the code or the function name. A one-line comment only for a non-obvious technical behaviour of a database or library (e.g. why a no-op update is used). Fix root causes; `async/await`, not promise chains; no lint suppression without reason.

## 8. Tests
- Apply the `test-design` skill (`../test-design/SKILL.md`) to every test you add or change: inventory existing tests first, one unique behaviour per test, lowest level that can prove it, no tests of library/tool guarantees, no duplicates across levels.
- **Unit:** every function with business logic, every path. Mock every dependency (spy on the module first, full module mocks last); assert calls with arguments and the return value; don't re-test callees. Providers and pure forwarding functions get no unit test. Parameterise instead of copying tests.
- **Mock the layer below, not a sibling model:** a model's unit test mocks its providers and clients, so each case is one mocked row (an expired rate = one row with a past date). Mocking another model forces `mockResolvedValueOnce` chains that assert the order of calls instead of the result.
- **Functional:** cover methods and queries end to end against a real test database (never mocked); mock every outbound HTTP call. A scenario per functional change and per bug fix; reuse the project's shared steps.
- **Never test the schema library:** don't create any test — unit or functional — whose only purpose is schema validation (wrong type, not an integer, missing or required field, enum, format, "full replace needs every field", a field missing from a batch item). The library already guarantees it; reviewers ask to delete these tests. Only rules the schema's types can't express (mutual exclusion, cross-field refinements) get a failure scenario.
  - This holds at **every entry point**: service/RPC methods, HTTP API and **webhook routes** (a scenario that posts an invalid payload only to get the framework's 400 from the route's input schema), queue/event consumers, CLI or job arguments. No unit test of a `schemas.ts` file either.
  - It also holds for **another service's schema**: don't mock a downstream validation error just to show it passes through. Mock it only when your code reacts to it in its own way (e.g. maps it to a non-retryable status), and then assert that reaction.
- A test that pins a temporary behaviour (fail-open while a field is optional) is named as such and changed by the follow-up that ends it; list it in that ticket.
- **Every failure scenario asserts why it failed:** the error message and code (or the error data listing the invalid fields), not just "failed"; skip unrelated side-effect checks after a failure.
- **No duplicate coverage:** before adding a scenario, list what each existing one proves; drop one that a combination of others already covers (link new + move existing ⇒ link existing).
- **Right level:** logic that runs entirely in the model before any query (de-duplication, normalisation, sorting) is proven by unit tests; functional fixtures use clean, already-normalised data so each scenario tests one thing.
- A date or threshold rule gets one test on each side of the boundary, with constants named by their side (`CREATED_BEFORE_END_DATE`, `CREATED_AFTER_END_DATE`).
- Names follow §10.

## 10. Naming and style (reviewer-preferred forms)
Follow the project's naming doc and the surrounding code first (test titles: the file's own, then its sibling files, then the repo's most common form, `../test-design/SKILL.md` Step 3); the forms below are defaults when there is nothing to copy. The content rules (domain words, condition as the caller sees it, asserted fields named, no vague verbs) apply in any form.
- **Feature/functional scenarios** (Gherkin keywords shown; other runners use the same words in their titles): `Feature: <Verb> <domain object>`; `Scenario: Should <verb> <object> [when <condition>]` in domain words, with the condition spelled out as the caller sees it (`Should update an existing <entity> when the update timestamp is newer than the stored one`, `Should unlink an existing <child> when the payload does not contain the <parent> ID`, `Should change the linked <parent> of a <child> when the upsert sends a different <parent> ID`, `Should create a placeholder <parent> and link the <child> to it when the actual <parent> does not exist yet`, `Should complete the information of a partially stored <entity>`). Compare with "the stored one", not "the existing one". Name the fields the scenario asserts (`Should return the <field> when …`), not "info" or "data". Custom-rule failures (never plain schema checks): `Should reject <what is wrong>`. No vague titles, no implementation words (table, column, SQL).
- **Unit tests:** `describe('<functionName>')`; `it('should <outcome> [when|without <condition>]')`, lower-case `should`, naming the exact outcome and the collaborator: `should return no <entities> without querying the database for an empty list`, `should throw <ErrorClass> '<message>' when <collaborator> throws`, `should throw <ErrorClass> and not call <next collaborator> when <collaborator> throws`. No vague verbs (fail, wrap, handle, work). Variants with `it.each(<namedList>)`.
- **Method definitions:** description = one sentence, verb first, what + guarantee (`Upsert <entities>, ensuring older notifications don't overwrite newer data.`). Success response description = `Returns the <past-participle> <entities>`.
- **Response fields** are named after the operation: `upserted<Entities>`, `created<Entity>`, `deleted<Entities>` — not a bare `<entities>` or a synonym the API doesn't use.
- **Schemas and types:** `<entity>Schema` + `type <Entity>`; `<method>RequestSchema` / `<method>ResponseSchema` + `<Method>Request` / `<Method>Response`; batch items `<method>InputSchema` / `<Method>Input`. A field that belongs to another entity — its uuid or its external id in a request — reuses that entity's field schema (`<entity>Schema.shape.<key>.nullish()`), never a redeclared primitive, so the two stay in sync.
- **Model / provider / handler names:** handlers follow the newest sibling's form; find-or-create of a link in a model is `resolve<Entity><Key>`; providers use `get` / `insert` / `update` / `upsert<Entities>If<Condition>`.
- **Files:** model functions in `models/<domain>/`; pure helpers (no I/O, e.g. normalising values) in `models/<domain>/helpers/` with tests in `helpers/__tests__/`.
- **Reuse the repo's vocabulary:** before naming a column, field or function, grep the repo for the same concept and reuse its word and its pair (`valid_from` → `valid_to`, `active_from` → `active_to`); no synonym the repo doesn't use (`until`, `end`, `expires`). A reused name brings its semantics: an interval end is exclusive (half-open `[from, to)`, active while `now < to`) unless the repo's existing pair says otherwise; store the first instant after the period (next local midnight), never `23:59:59.999`, which rounding to the column's precision silently moves. Say the boundary and time zone in the PR.
- **Short names:** a file or function name is as short as its scope allows. When a new file handles another variant of what an existing module parses or syncs, extend that module or keep its family name; a name chaining every qualifier (`parse<Source><Entity><SubEntity><Field>Attributes`) signals a split nobody needs. Constants too: name what the set holds (`COUNTRIES_WITHOUT_<FEATURE>`), not the decision around it (`<FEATURE>_EXCLUDED_COUNTRY_CODES`).
- **A rename lands everywhere in the same round:** column, record and API fields, function, file, type and constant names, log prefixes, across every stacked PR. Names owned by another system (a third party's attribute key) keep that system's word; the parser of that data is where the word changes.
- **Consistency over invention:** before choosing an edge-case behaviour (empty batch, not found, duplicates), check how sibling methods behave and align (e.g. an empty batch returns an empty array, not an error). Reviewers ask "what do the other methods do?". The same holds for lifecycle flags: when a sibling already reads the same entity (an active flag, an end date, a deleted marker), check what it checks (`isActive`, `validTo`) and apply the same rule or say in the PR why this path differs. When the right answer for the extra state is not obvious (return 0 or an error for an inactive source?), ask in the PR instead of choosing silently.

## 9. Scope and PRs
- Touch only what the task needs: no drive-by refactors, renames or formatting; open a ticket for unrelated issues. In code the change must touch anyway, bring the touched types and signatures up to the standards (e.g. a record aliased to an API type, an exported one-off input alias); leave untouched statements (such as an old log line) as they are. A migration PR holds only the migration; code using it ships next and names the order.
- Small PRs, one topic, draft until ready; never bypass hooks; tests included. Conventional Commit title with the scope the project uses. Keep the description true after every push: re-read it against the code (behaviour on missing fields, defaults, test counts, release order).
- The PR description says where a new rule is **not** enforced (paths that rely on another system to check it), and lists the manual steps needed before the production release (config to create in a third-party tool, with the exact value).
- Before each commit read the staged file list: no tool output (test reports, caches, IDE files, build output) is committed. An ignore rule belongs in this PR only when this PR's own commit added such a file; otherwise it goes to its own PR.
- In review threads say "done" only for pushed code; link the guideline instead of re-arguing.
- A pin on another component's prerelease build is a merge blocker: the PR says so with the release order, and the released version replaces it before merge. Recompile and re-check behaviour then: the prerelease may predate the provider's last review fixes (a renamed field, a changed boundary).
- Handle only the events and inputs the ticket's data needs. A pre-existing gap you notice (an unhandled event type, an old status code) goes to its own ticket, not into this PR.
- Don't delete or reshape existing code that feeds data other teams rely on (tracking, reporting, support tools), even when the result is equal: a reviewer can verify one added line faster than a removed guard. When a type change forces an adjustment, keep the code and adapt at the call site (`?? <default>`). If you must delete lines that look like removing data, say in the PR description what is still sent and why.

## 11. Abstractions and reuse ("why do we need this?")
- No single-use abstractions. A mapper, helper, wrapper or file earns its own place only if it is reused, has enough logic to deserve its own tests, or names a meaningful domain conversion; otherwise keep the transformation inline where it is consumed.
- Don't wrap an existing client call in a one-line function; call the client where it is needed.
- **One rule, one helper:** before writing a check (expiry, eligibility, an active window), grep the sibling modules for the same rule. When one has it, move it to a pure helper in `models/<domain>/helpers/` with its test in `helpers/__tests__/` and use it in both places; two copies drift. The reverse also holds: logic called from one place stays inline.
- Don't move a handler's core flow into internal helpers with return-value protocols (`returns<X> | undefined`); keep the flow readable in one place.
- Shared values are generic: a response message used by several handlers is one constant in the shared constants module, not a per-route dictionary; a failure kind several flows share gets one parameterised error class (`<Kind>Error({ message, cause, info })`), not one class per flow.
- Prefer the simplest code the source's contract allows. Every extra layer, check, branch or changed log line must answer "why do we need this?" before you push.
